# GW2 resolver reaction-layer implementation specification

## Status

Proposed. This document requires one final architecture review before implementation.

Baseline reviewed: the working tree on 2026-08-07. The scheduler and event-materializer
changes already present in that tree are treated as the current architecture, not as work
owned by this proposal.

## Purpose

Remove relic, resolver-time sigil, and food policy from generic GW2 resolver handlers
without changing combat behavior. Profession reactions and common equipment reactions
will be composed once into a typed, ordered resolver-stage registry.

This is dependency and lifecycle cleanup. It is not a balance or event-model migration.

## Problem statement

The shared resolver currently has two dispatch styles:

1. profession behavior is supplied through `eventReactions` and selected dynamically;
2. common equipment behavior is imported and called at specific resolver locations.

The second style causes generic modules to know which subsystems participate in each
lifecycle point:

- `resolver/event-handlers.ts` imports six relic wrappers, food data, food timing logic,
  and contains the resolver-side Severance special case;
- `resolver/condition-resolution.ts` calls relic condition handling directly;
- `resolver/hit-resolution.ts` imports the relic strike multiplier;
- `resolver/resolve-timeline.ts` imports passive relic timeline handling; and
- `resolver/runtime-state.ts` constructs relic, sigil, and food state directly.

Relics themselves are already data-driven. `RELIC_RULES`, `createRelicRuntime()`, and
`invokeRelicHook()` select and dispatch the active relic rule. This proposal retains that
mechanism and replaces only its scattered resolver wiring.

Condition reactions have a second, intentional asymmetry. They run after each successful
condition application rather than once per queued `condition` event. This is necessary
because nested applications generated by relics call `applyCondition()` directly. The
contract exists in code but is not named or tested as an explicit resolver lifecycle stage.

## Decision summary

Implement a GW2-local, stage-aware reaction registry.

- Event-driven profession and equipment effects use one ordered registry.
- Condition reactions dispatch from the successful-application boundary.
- Numeric queries and pre-resolution timeline work remain explicit capabilities; they are
  not disguised as event reactions.
- Existing profession reaction keys may be supported through a central adapter only during
  intermediate migration commits. The adapter and all legacy keys must be removed before
  this implementation is considered complete.
- Existing event types, public result shapes, proc identities, and random-number order must
  not change.

## Goals

- Make generic event handlers dispatch lifecycle stages without naming relic, sigil, or
  food functions.
- Preserve the exact current order of base resolution, equipment effects, profession
  reactions, derived-event insertion, and recursive condition application.
- Make successful condition application an explicit, documented stage.
- Compose the selected profession and common equipment contributions once in
  `declarative-simulation.ts`.
- Retain the existing `RELIC_RULES` plug-in model.
- Allow a new equipment reaction at an existing stage to be registered without modifying
  its generic handler.
- Reject duplicate hook IDs and provide deterministic ordering.
- End with every profession reaction authored against canonical resolver stages, with no
  compatibility adapter or legacy-key fallback.
- Add direct tests for hook order and condition recursion instead of relying only on final
  DPS assertions.

## Non-goals

- Do not alter coefficients, durations, cooldowns, proc probabilities, or ownership rules.
- Do not change canonical event names or scheduler-to-resolver handoff data.
- Do not move sigil proc generation out of `platform/gw2/scheduler`.
- Do not combine static food or sigil attribute calculation with resolver reactions.
- Do not replace `RELIC_RULES` with one rule object per event type.
- Do not route `strikeMultiplier`, `conditionDurationBonus`, or passive timeline generation
  through event reactions.
- Do not migrate the separate Elementalist simulator.
- Do not retain a long-lived compatibility path for legacy profession reaction keys.
- Do not change the engine-wide profession hook contract unless a concrete blocker is found.

## Required behavioral invariants

The implementation must preserve all of the following.

### Damage order

For each `damage` event:

1. build the hit-resolution context, including the existing critical fact;
2. apply and record base strike damage;
3. run the relic `damageResolved` hook;
4. run the profession `damage` reaction;
5. evaluate and, when eligible, enqueue the critical-hit food proc;
6. run the relic `afterHit` hook.

Food must consume the same critical fact as profession and sigil behavior. Moving the food
hook must not add, remove, or reorder random draws. A generated food event must still be
decorated by the profession `food_proc` reaction before it is enqueued.

### Buff order

For each `buff` event:

1. insert the boon application and compute active stacks;
2. update `ctx.sigil.severanceUntil` when `kind === "sigil-severance"`;
3. run the relic boon hook;
4. run the profession `buff` reaction.

Expired boon applications remain available for historical queries exactly as they are now.

### Condition-application order

A condition draft with positive stacks and positive resolved duration must:

1. compute and snapshot duration;
2. create the resolved application;
3. append it to result and condition state;
4. schedule its tick events;
5. dispatch the profession condition reaction;
6. dispatch the relic condition hook;
7. return the resolved application.

Zero-stack or zero-duration drafts must return `null` without dispatching the application
stage.

Any nested condition created by a relic must call the same `applyCondition()` function. It
must therefore repeat the complete successful-application sequence, including profession
reactions. Existing relic source/identity guards remain responsible for preventing invalid
self-trigger loops.

### Other existing order

| Resolver stage | Required hook order |
| --- | --- |
| `blast-combo.resolved` | relic blast-combo hook |
| `buff.applied` | sigil Severance state, relic boon, profession buff |
| `damage.resolved` | relic damage-resolved, profession damage, food, relic after-hit |
| `condition.applied` | profession condition, relic condition |
| `condition-tick.resolved` | profession condition-tick |
| `control.resolved` | relic control, profession control |
| `blind.resolved` | profession blind |
| `peitha.resolved` | relic Peitha, profession Peitha |
| `weapon-set.changed` | profession weapon-set reaction after common state update |
| `food-proc.created` | profession food-proc decorator before enqueue |

Stable registration order breaks ties between hooks with equal numeric order.

## Target architecture

```text
resolve profession runtime
          |
          +-- existing composed profession eventReactions
          |
          +-- createGw2ResolverExtensions(...)
                  |
                  +-- stage reaction registry
                  |     +-- canonical profession stage hooks
                  |     +-- relic reaction adapters
                  |     +-- resolver-side sigil adapters
                  |     +-- food reaction adapters
                  |
                  +-- equipment state factory
                  +-- strike multiplier capability
                  +-- condition-duration capability
                  +-- pre-resolution timeline capability
          |
          +-- query, hit resolution, condition resolution,
              generic event handlers, and timeline resolver
```

The composition root owns subsystem assembly. Generic numeric modules receive typed
capabilities and do not import concrete relic, food, or sigil policy.

## Proposed contracts

Add the following concepts to `platform/gw2/types.d.ts`. Exact names may change during
implementation, but the separation and semantics are normative.

```ts
export type Gw2ResolverStage =
  | "blast-combo.resolved"
  | "buff.applied"
  | "damage.resolved"
  | "condition.applied"
  | "condition-tick.resolved"
  | "control.resolved"
  | "blind.resolved"
  | "peitha.resolved"
  | "weapon-set.changed"
  | "food-proc.created";

export interface Gw2ResolverReactionHook {
  readonly id: string;
  readonly order: number;
  readonly handler: Gw2ResolverReaction;
}

export type Gw2ResolverReactions = Readonly<
  Partial<Record<Gw2ResolverStage, Gw2ResolverReaction>>
>;

export function defineGw2ResolverReactions<
  const T extends Readonly<Record<string, (...args: never[]) => unknown>>,
>(
  reactions: T & Record<Exclude<keyof T, Gw2ResolverStage>, never>,
): Readonly<T>;

export type Gw2ResolverReactionContributions = Readonly<
  Partial<Record<Gw2ResolverStage, readonly Gw2ResolverReactionHook[]>>
>;

export interface Gw2ResolverReactionRegistry {
  dispatch(
    stage: Gw2ResolverStage,
    context: Gw2ResolverRuntime,
    event: Gw2ResolverEvent,
    details?: SchedulerRecord,
  ): SchedulerRecord | void;
}

export interface Gw2ResolverExtensions {
  readonly reactions: Gw2ResolverReactionRegistry;
  readonly createEquipmentState: (
    config: Gw2Config,
  ) => Pick<Gw2ResolverRuntime, "relic" | "sigil" | "food">;
  readonly strikeMultiplier: (
    context: Gw2ResolverRuntime,
    event: Gw2ResolverEvent,
  ) => number;
  readonly conditionDurationBonus: (
    context: Gw2QueryRuntime,
    at: number,
  ) => number;
  readonly beforeResolveTimeline: (
    context: Gw2ResolverRuntime,
    events: readonly Gw2ResolverEvent[],
    rotationEndTime: number,
  ) => void;
}
```

`Gw2ResolverReactions` replaces the current open `Record<string, ...>` runtime type. Direct
profession-authored maps must use `defineGw2ResolverReactions()`. Its exact-key constraint
makes misspelled or legacy keys fail at TypeScript declaration sites while preserving each
handler's narrower profession-specific context and detail types. Its runtime implementation
must also reject unknown keys and non-function values, so JavaScript modules receive the same
protection without relying only on JSDoc. Registry construction must independently reject
unknown keys, covering values that cross an engine-generic boundary.

The registry must return the last non-`undefined` hook result, matching the current engine
`createEventReactions()` behavior. This matters for `food_proc`, whose profession reaction
may return fields that decorate the generated event.

Prefer adapting the engine's existing `createEventReactions()` ordering and duplicate-ID
validation rather than implementing a subtly different sorter. If TypeScript adaptation
would require broad unsafe casts or engine contract changes, implement a small GW2-local
normalizer with identical behavior and focused tests.

## Stage composition

Add `platform/gw2/resolver/reaction-registry.ts` to:

- accept canonical profession resolver stages;
- combine profession and equipment hook descriptors;
- normalize each stage once;
- reject duplicate hook IDs within a stage; and
- expose only `dispatch()` after construction.

The following mapping is permitted only as a temporary migration scaffold:

| Legacy profession key | Canonical resolver stage |
| --- | --- |
| `buff` | `buff.applied` |
| `damage` | `damage.resolved` |
| `condition` | `condition.applied` |
| `condition_tick` | `condition-tick.resolved` |
| `control` | `control.resolved` |
| `blind` | `blind.resolved` |
| `peitha` | `peitha.resolved` |
| `weapon_set` | `weapon-set.changed` |
| `food_proc` | `food-proc.created` |

The scaffold must be private to the registry implementation, clearly marked as temporary,
and deleted in the profession-key cutover phase. It must not be exported, documented as a
supported API, or accepted by the final `Gw2ResolverReactions` type.

The final registry accepts only canonical stage keys and throws on every unknown key. Do not
dispatch keys that the current handlers do not invoke. Supporting a new profession lifecycle
stage requires an explicit behavior change and separate tests.

All direct profession reaction maps must migrate to canonical stage keys. The GW2-native
`NativeResolvedReaction` authoring contract must also become stage-native: replace its
`eventType: string` field with `stage: Gw2ResolverStage`, update its compiler to index by
`declaration.stage`, and make helpers such as `onResolvedDamage()` emit
`"damage.resolved"`. This is a GW2-native contract correction; it does not require changing
the engine-wide event-handler contract.

Use named order bands so ordering remains readable:

```ts
const REACTION_ORDER = Object.freeze({
  EARLY_COMMON: -200,
  COMMON: -100,
  PROFESSION: 0,
  LATE_COMMON: 100,
  FINAL_COMMON: 200,
});
```

IDs must describe ownership, for example `sigil.severance`, `relic.boon`,
`profession.damage`, `food.critical-strike`, and `relic.after-hit`.

## Equipment adapters

Add `platform/gw2/resolver/equipment-reactions.ts`. This is the only resolver module that
may import resolver-time food data and the event-driven relic wrappers.

It must provide hook descriptors for:

- Severance state updates after common boon insertion;
- relic boon, blast-combo, damage-resolved, after-hit, condition, control, and Peitha
  hooks; and
- critical-strike food evaluation and proc generation.

The existing relic wrappers may remain public during migration. Removing redundant wrappers
is optional cleanup after all consumers and tests have migrated.

The food hook needs to dispatch `food-proc.created` before enqueueing its derived damage
event. Avoid a mutable registry or an uninitialized circular reference. Accept one of these
designs:

1. inject a stable `dispatch` closure into the equipment-reaction factory; or
2. split food-event decoration into a typed decorator capability composed beside the stage
   registry.

The first option is preferred if the registry factory can guarantee that no hook executes
during construction. Whichever option is chosen must be covered by a direct construction
and dispatch test.

## Condition application

Replace `onConditionApplied` with the stage registry, or rename it to
`afterConditionApplied` if retaining a narrow callback produces a simpler dependency graph.
The required behavior is the same in either design:

```ts
// Dispatched exactly once for every successful condition application,
// including recursively generated applications. State and ticks already
// exist when hooks run. Rejected drafts do not dispatch.
reactions.dispatch("condition.applied", ctx, application, {
  application,
  activeConditionStackCount,
  applyCondition,
});
```

There must be only one condition-application dispatch site. The ordinary `condition` event
handler calls `applyCondition()` and must not dispatch the stage again.

Use the normal resolver `applyCondition` function in hook details. The current
`applyRelicCondition` alias exists only to bridge narrower relic context typing; remove it if
the capability types can express the shared function safely.

## Non-event capabilities

Event stages do not replace synchronous calculations.

### Strike multiplier

Change `createGw2HitResolution()` to accept a `strikeMultiplier` dependency. Its default, if
one is allowed, must be the identity function returning `1`; production construction must
pass `extensions.strikeMultiplier` explicitly.

`resolver/hit-resolution.ts` must no longer import `relic-rules.ts`.

### Condition-duration bonus

Pass `extensions.conditionDurationBonus` into `createGw2CombatQuery()`. Preserve the current
timing and combination with active sigil bonuses and Aristocracy-specific behavior.

Do not move duration queries into `condition.applied`; duration is computed before an
application exists.

### Passive timeline hook

Pass `extensions.beforeResolveTimeline` into `resolveGw2Timeline()` and invoke it at the
current location before the event queue is drained. `resolve-timeline.ts` must not import
`relic-rules.ts` directly.

### Equipment runtime state

Use `extensions.createEquipmentState(config)` while building the resolver runtime. Preserve
the public runtime fields:

```ts
{
  relic,
  sigil: { severanceUntil: 0 },
  food: { criticalProgress: 0, readyAt: 0 },
}
```

Changing those fields or nesting them under a new object is outside this proposal.

## Composition-root changes

In `platform/gw2/declarative-simulation.ts`:

1. resolve the active profession runtime as today;
2. create `Gw2ResolverExtensions` using its already-composed `eventReactions`;
3. pass the condition-duration capability into query construction;
4. pass the strike capability into hit-resolution construction;
5. pass the same reaction registry into condition resolution and event handlers;
6. use the equipment state factory when creating resolver state; and
7. pass the pre-resolution timeline capability into `resolveGw2Timeline()`.

The extensions object must be created once per simulation pass. Do not independently compose
reaction registries for handlers and condition resolution.

## Generic handler result

After migration, `resolver/event-handlers.ts` should:

- retain common numeric and state transitions;
- dispatch named resolver stages with the details already available at each point;
- contain no imports from `relic-rules.ts` or `gear-data.ts`;
- contain no food cooldown, progress, random-roll, event-construction, or proc-recording code;
  and
- contain no `sigil-severance` branch.

It is acceptable for this file to dispatch more than one named stage across different
handlers. It is not acceptable for it to know which subsystem consumes a stage.

## File-level implementation plan

### New files

- `js/platform/gw2/resolver/reaction-registry.ts`
  - typed stage dispatch;
  - deterministic composition;
  - temporary legacy-key mapping during migration only; the final file must not contain it.
- `js/platform/gw2/resolver/equipment-reactions.ts`
  - event-driven relic adapters;
  - resolver-time Severance adapter;
  - critical-hit food adapter.
- `tests/gw2-resolver-reactions.test.js`
  - direct registry, order, and condition-lifecycle tests.

An `extensions.ts` facade may be added if keeping construction in the two proposed resolver
files would otherwise leak subsystem assembly back into `declarative-simulation.ts`.

### Modified files

- `js/platform/gw2/types.d.ts`
  - add stage, hook, registry, extension, and dependency types;
  - close `Gw2ResolverReactions` over `Gw2ResolverStage`.
- `js/platform/gw2/native-profession.ts`
  - make `NativeResolvedReaction` use a typed `stage` instead of an open `eventType`;
  - make resolved-reaction helpers emit canonical stage names.
- `js/platform/gw2/declarative-simulation.ts`
  - compose extensions once and inject them.
- `js/platform/gw2/resolver/event-handlers.ts`
  - replace subsystem calls with stage dispatches.
- `js/platform/gw2/resolver/condition-resolution.ts`
  - dispatch exactly once after each successful application.
- `js/platform/gw2/resolver/hit-resolution.ts`
  - inject the strike-multiplier capability.
- `js/platform/gw2/resolver/runtime-state.ts`
  - construct equipment state through the injected factory.
- `js/platform/gw2/resolver/resolve-timeline.ts`
  - invoke the injected pre-resolution hook.
- `js/platform/gw2/resolver/index.ts`
  - export only contracts intended for platform consumers.
- `js/platform/gw2/query.ts`
  - consume the injected condition-duration capability.
- `js/platform/gw2/relic-rules.ts`
  - only typing/export cleanup required by adapters; retain `RELIC_RULES` and
    `invokeRelicHook()`.
- profession reaction declarations under `js/professions/**`
  - rename legacy reaction keys to canonical resolver stages;
  - construct direct maps with `defineGw2ResolverReactions()`.
- `tests/resolver-architecture.test.js`
  - retain and, where necessary, strengthen end-to-end equipment behavior tests;
  - assert canonical reaction keys for Core and every elite runtime.
- `tsconfig.build.json`
  - add new source files if the build still requires explicit inclusion.

## Implementation sequence

### Phase 1: Characterization tests

Before moving production behavior:

- assert exact damage-stage hook order using trace-only test hooks;
- assert exact buff-stage hook order;
- assert successful versus rejected condition dispatch counts;
- assert a relic-created condition reaches a profession condition reaction;
- preserve existing seeded food results and random consumption;
- preserve existing Severance timing and damage; and
- preserve same-timestamp derived-event queue ordering.

The production refactor must begin from a green baseline.

### Phase 2: Registry without behavior migration

- Add types and registry normalization.
- Add legacy profession-key adaptation as a private, explicitly temporary scaffold.
- Unit-test ordering, missing stages, duplicate IDs, stable ties, and return semantics.
- Keep existing handler calls temporarily.

This phase is not merge-complete on its own. No release or completed implementation may
retain the temporary adapter.

### Phase 3: Condition lifecycle

- Route profession and relic condition hooks through `condition.applied`.
- Remove the direct relic call from condition resolution.
- Remove the constructor callback in `declarative-simulation.ts` if the registry replaces it.
- Add recursion and no-dispatch-on-rejection tests.

### Phase 4: Event-driven equipment migration

Move one stage at a time, running focused tests after each:

1. blast combo;
2. buff, including Severance;
3. control and Peitha;
4. damage-resolved and after-hit relic behavior;
5. critical-hit food and food-proc decoration; and
6. remaining profession-only dispatches.

Delete direct subsystem imports only after the corresponding behavior is registered.

### Phase 5: Profession reaction-key cutover

- Rename every direct profession reaction key to its canonical `Gw2ResolverStage` value.
- Change `NativeResolvedReaction.eventType` to a typed `stage` field and update the native
  compiler and helper constructors.
- Require direct TypeScript and JavaScript maps to use
  `defineGw2ResolverReactions()`, preserving specialized handler signatures while enforcing
  exact canonical keys.
- Change `Gw2ResolverReactions` from an open string record to
  `Partial<Record<Gw2ResolverStage, Gw2ResolverReaction>>`.
- Make registry construction throw on unknown stage keys.
- Add a conformance test that resolves every native family in Core mode and once for every
  entry in its `specializationIds`, then asserts that every reaction key is canonical.
- Delete the legacy-key mapping and all compatibility-only tests in the same phase.

The cutover is atomic from the final branch's perspective. The adapter may exist between
local commits, but it must never be the final state of the implementation PR.

### Phase 6: Non-event capability injection

- inject strike multiplier;
- inject condition-duration bonus;
- inject passive timeline processing; and
- inject equipment runtime-state creation.

Do not combine these into the reaction stage map.

### Phase 7: Cleanup and documentation

- remove the local `reactionFor()` helper;
- remove obsolete callback and alias types;
- verify that no legacy-key adapter, mapping constant, fallback, or compatibility test
  remains;
- remove relic wrapper exports only when no consumer remains;
- update `docs/ARCHITECTURE.md` with the stage/capability distinction; and
- verify there are no new circular imports.

## Test matrix

| Area | Required coverage |
| --- | --- |
| Registry | missing stage is a no-op; numeric order; stable tie order; duplicate ID rejection; last defined return |
| Damage | base resolution precedes hooks; current four-part hook order; hit context shared unchanged |
| Food | deterministic accumulator; ICD retention; stochastic seeded rolls; profession decoration; source/icon/proc record |
| Buff/sigil | boon insertion precedes Severance; relic precedes profession; historical boon queries unchanged |
| Conditions | rejected draft; direct application; nested relic application; state visible to hooks; tick scheduling precedes hooks |
| Relics | blast, boon, control, Peitha, damage-resolved, after-hit, duration, strike, passive timeline |
| Profession | canonical stage keys only; Core plus every elite checked; module hook order preserved; unknown keys rejected |
| Queue | same-timestamp derived events retain causal insertion order |
| Runtime | equipment state is isolated per simulation and retains the existing public shape |

Prefer direct registry/condition tests for ordering and existing architecture tests for final
combat outcomes. Do not make every ordering test depend on one profession's traits.

## Validation commands

Run from the repository root:

```powershell
npm run build
npm run typecheck
npm test -- tests/gw2-resolver-reactions.test.js
npm test -- tests/resolver-architecture.test.js
npm run check
npm test
```

`npm run check` rebuilds the project. Running both the focused tests and the complete suite is
intentional: the focused tests diagnose stage failures, while the full suite detects seeded
randomness, event-order, profession, and UI regressions.

## Acceptance criteria

Implementation is complete only when:

- all existing and new tests pass;
- all validation commands pass;
- the shared resolver produces unchanged outputs for existing deterministic and seeded
  stochastic fixtures;
- generic event handlers contain no relic, food, or Severance policy;
- condition application has one documented post-application dispatch site;
- nested relic applications invoke profession condition reactions exactly once per accepted
  application;
- sigil event generation remains in the scheduler;
- numeric query and timeline capabilities remain outside the event stage registry;
- hook ordering is explicit and covered by tests;
- the registry is composed once per simulation pass;
- no legacy profession-key adapter, fallback, mapping, or compatibility-only test remains;
- no legacy reaction key remains in profession declarations;
- all direct TypeScript and JavaScript reaction maps use
  `defineGw2ResolverReactions()`;
- registry construction rejects unknown stage keys;
- the reaction-stage conformance test covers Core and every elite runtime; and
- no new circular dependency or unsafe mutable-construction dependency is introduced.

## Risks and mitigations

### Hook reordering

Risk: a visually equivalent registry order changes state observed by later hooks.

Mitigation: encode the current order numerically and assert trace order directly.

### Random stream drift

Risk: moving food logic changes whether or when `food.critical-strike` consumes a roll.

Mitigation: retain all eligibility checks and hook position; compare seeded results and, if
needed, a recorded random-label trace.

### Condition double dispatch

Risk: both the `condition` handler and `applyCondition()` dispatch the same stage.

Mitigation: make `applyCondition()` the only dispatch site and test one direct queued event.

### Recursive condition loops

Risk: central composition changes relic source guards or applies the relic hook twice.

Mitigation: retain existing relic rule guards unchanged and test a nested application trace.

### Food decorator construction cycle

Risk: food needs the registry to dispatch `food-proc.created` while the registry is being
constructed from food hooks.

Mitigation: use a stable injected dispatcher whose target is fully compiled before any hook
can execute, or use a separate typed decorator capability. Do not expose a partially built
mutable registry.

### Scope creep into scheduler sigils

Risk: the phrase "sigil reaction" encourages moving proc materialization back into resolver
handlers.

Mitigation: migrate only the resolver-side Severance state update. Scheduler-owned sigil
generation is explicitly out of scope.

### Temporary adapter becomes permanent

Risk: the migration adapter is treated as harmless compatibility infrastructure and survives
the refactor.

Mitigation: make adapter deletion a numbered implementation phase and a blocking acceptance
criterion. Close the reaction-key type, reject unknown keys at runtime, and enumerate every
native Core/elite runtime in an architecture test. The final reviewing LLM must request
changes if any adapter or legacy key remains.

## Questions for the final reviewing LLM

The reviewer should return `APPROVE` or `REQUEST CHANGES`, followed by blocking findings in
severity order. It must return `REQUEST CHANGES` if the final implementation retains a
legacy-key adapter, legacy reaction declaration, or open string-keyed GW2 reaction type. It
should specifically verify:

1. Does the proposed stage model preserve every current execution-order boundary?
2. Is `condition.applied` located correctly for direct and recursively generated
   applications, with no double dispatch?
3. Are strike multiplier, duration queries, state construction, and passive timeline work
   correctly excluded from the event reaction registry?
4. Does the food-proc decorator design avoid an initialization cycle while preserving
   pre-enqueue profession updates?
5. Is seeded random-number consumption guaranteed to remain stable?
6. Does the plan respect the current scheduler ownership of sigil proc generation?
7. Are any affected production files, types, build inputs, or regression tests missing?
8. Can the same result be achieved with materially less machinery without restoring direct
   subsystem imports to generic handlers?
9. Do any proposed interfaces create a dependency direction from generic resolver code back
   into concrete equipment policy?
10. Are the acceptance criteria strong enough to distinguish structural cleanup from a
    behavior change?
11. Does the final implementation contain only canonical stage keys, with the temporary
    adapter and its compatibility tests deleted?

Non-blocking naming preferences should be separated from correctness or architecture
failures.
